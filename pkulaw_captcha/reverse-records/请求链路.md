# pkulaw.com 腾讯 Turing 验证码 + 邮箱验证码 请求链路

目标页面：https://www.pkulaw.com/case?way=topGuid（点击登录 -> 短信/邮箱登录弹窗 -> 腾讯验证码）

## 已确认的完整请求链路（真实抓包，2026-07-29）

```
1. GET  https://cas.pkulaw.com/auth/realms/fabao/protocol/openid-connect/auth?...
        （打开登录 iframe，拿到 keycloak session cookie：AUTH_SESSION_ID / KC_RESTART 等）

2. GET  https://turing.captcha.qcloud.com/cap_union_prehandle?
        aid=195551051&protocol=https&accver=1&showtype=popup&
        ua=<base64(UA字符串)>&noheader=1&fb=0&aged=0&enableAged=0&
        enableDarkMode=0&grayscale=1&clientype=2&cap_cd=&uid=&lang=en&
        entry_url=<urlencode(https://cas.pkulaw.com/auth/realms/fabao/protocol/openid-connect/auth)>&
        elder_captcha=0&js=%2Ftcaptcha-frame.91efdf16.js&login_appid=&
        wb=1&subsid=1&callback=_aq_362565&sess=
        —— JSONP，返回验证码本次挑战的全部配置（见下方 response）

3. GET  https://turing.captcha.qcloud.com/tdc.js?app_data={sid}&t={随机}
        —— 核心环境采集+加密SDK，重度混淆（JSVMP，见下方分析）

4. GET  https://turing.captcha.qcloud.com/cap_union_new_getcapbysig?
        img_index=1&image={image_id}&sess={sess}
        —— 取验证码背景图（PNG二进制）

5. （用户完成点选交互，tdc.js 在后台持续采集鼠标/环境数据）

6. POST https://turing.captcha.qcloud.com/cap_union_new_verify
        Content-Type: application/x-www-form-urlencoded
        body: collect=...&tlg=2008&eks=...&sess=...&ans=[{...}]&
              pow_answer=c03144eec4874e11#149864&pow_calc_time=285
        —— 提交验证结果，成功返回 {"errorCode":"0","randstr":"@Gkc","ticket":"tr0327...","sess":""}

7. POST https://cas.pkulaw.com/auth/realms/fabao/sms/code/send-email
        ?email={邮箱}&randstr={来自步骤6}&ticket={来自步骤6}
        —— 用 randstr+ticket 验证腾讯验证码通过，触发发送邮箱验证码
        响应: {"expiresIn":300}

8. POST https://cas.pkulaw.com/auth/realms/fabao/sms/code/verify-email
        ?email={邮箱}&code={用户输入的验证码}
        —— 验证邮箱验证码
        响应（验证码错误时）: {"error":"CodeNotExist"}
        —— 用户确认：拿到这个响应本身就说明前面腾讯验证码 + send-email 两步已经成功
           （如果验证码环节没过，根本走不到这一步）
```

## 关键接口的完整参数（reqid 对应本次抓包会话，仅供参照）

### cap_union_prehandle 响应（JSONP，回调名 _aq_362565）
```json
{
  "state": 1,
  "capclass": "1",
  "subcapclass": "2404",
  "sess": "s0i6b3dd...",
  "sid": "1685959396487598080",
  "data": {
    "comm_captcha_cfg": {
      "tdc_path": "/tdc.js?app_data=1685959396487598080&t=691719213",
      "pow_cfg": {
        "prefix": "c03144eec4874e11#",
        "md5": "558cafa46f92f9613d595e0a197139eb"
      }
    },
    "dyn_show_info": {
      "instruction": "请依次点击：箔 岔 编 ",
      "bg_elem_cfg": {
        "size_2d": [672, 480],
        "click_cfg": {"mark_style": "inc_number", "data_type": ["DynAnswerType_POS"]},
        "img_url": "/cap_union_new_getcapbysig?img_index=1&image=...&sess=..."
      }
    }
  }
}
```
**验证码类型**：点选文字型（"请依次点击：箔 岔 编"），提交时 `ans` 字段是按点击顺序排列的坐标数组：
```json
[{"elem_id":1,"type":"DynAnswerType_POS","data":"543,225"},
 {"elem_id":2,"type":"DynAnswerType_POS","data":"252,252"},
 {"elem_id":3,"type":"DynAnswerType_POS","data":"250,146"}]
```
跟 wkinfo 的 clickWord 是同一类验证码（点选N个字），图像识别部分（找字在图上的坐标）可以复用类似
ddddocr 的思路，这部分不难。

**pow_cfg 是一个纯算法可解的工作量证明题**（好消息——这部分不需要浏览器环境）：
`prefix="c03144eec4874e11#"`，`md5="558cafa46f92f9613d595e0a197139eb"`，最终提交的
`pow_answer="c03144eec4874e11#149864"`。即：本地爆破整数 N（从0开始），计算
`md5(prefix + str(N))`，直到等于目标 md5 值，找到后 `pow_answer = prefix + str(N)`，
`pow_calc_time` = 爆破耗时（毫秒）。纯 Python 就能做，不需要 JS。

### cap_union_new_verify 请求体（POST, x-www-form-urlencoded）
```
collect=<urlencode(超长字符串，看起来是 base64/自定义编码的二进制blob)>
tlg=2008
eks=<超长字符串，同样是加密/编码后的blob>
sess=<来自 prehandle 响应的 sess>
ans=<JSON数组，点击坐标，见上>
pow_answer=<prefix#nonce>
pow_calc_time=<毫秒数>
```
**`collect` 和 `eks` 是本次逆向的真正难点**：来自 tdc.js 内部的环境采集与加密逻辑，不是简单的
AES/MD5 能直接套的。

### tdc.js（核心难点，已确认是 JSVMP 混淆）
`https://turing.captcha.qcloud.com/tdc.js?app_data={sid}&t={随机数}`，gzip 后仍有 ~30KB。
开头就是一个自定义字节码虚拟机：
```js
var __TENCENT_CHAOS_STACK = function(){
  function __TENCENT_CHAOS_VM(S,Q,z,D,C,w,y,I){ ... /* opcode dispatch loop */ ... }
  ...
  return __TENCENT_CHAOS_VM(0, function(l){ /* 解码传入的 base64 风格字符串为字节码数组 */ }(["Pw..."]))
}
```
`__TENCENT_CHAOS_VM` 是一个标准的栈式字节码解释器（opcode 分派数组 `A[...]`，每个元素是一个闭包，
对应一条"指令"：加减乘除、属性读写、函数调用、跳转等），真正的采集/加密逻辑被编译成了塞进字符串常量
里的自定义字节码，不是可读的 JS 源码。这是典型的 **JSVMP（JS 虚拟机保护）**。

## 验证结果（2026-07-29，真实提交，非模拟）

按用户确认的方案二（POW+OCR 用 Python 实现；collect/eks 用最小化 Node 沙箱真实跑 tdc.js
本身，不做 opcode 级还原）实现了完整链路，代码见 `pkulaw_captcha/`：

- `pow_solver.py` —— 纯 Python MD5 爆破，跟真实抓包数据核对完全一致
- `recognize.py` —— ddddocr det()+三模型分类取并集，识别点选坐标（同 wkinfo clickWord 套路）
- `tdc_bridge.js` + `tdc_client.py` —— Node `vm` 沙箱（非浏览器/非Puppeteer/Selenium，
  只有十几个手写 stub：window/document/navigator/screen/location/canvas-2d/localStorage）
  加载 tdc.js 原始代码后，直接调用它自己的 `window.TDC.getData(true)` / `getInfo()`
- `captcha_client.py` —— 编排 prehandle -> OCR -> tdc collect/eks -> pow -> 提交 verify

**真实提交测试结果**（`python captcha_client.py`）：连续 2 次 OCR 没能识别全部目标字
（"抱 膊 澄"、"采 斥 裁"，换新挑战重试），第 3 次识别成功并提交，服务端返回：
```json
{"errorCode":"0","randstr":"@MUH","ticket":"tr03QJsMFMn1HgR3o3p-U6CrCm0WzR06rmAd54puZ2cZdbhESHETyskmK54DB6xnStBDkLBgJMOBTM1qpJtIG-MOC2fcts21EVClMjUX1igoeNa0A7fpUTnacfKVBGCE8hzGYOba9JzX3Lo*"}
```
`errorCode:"0"` 是真实的验证通过响应，说明这套"POW/OCR纯算法 + tdc.js 本身在极简 Node
沙箱里真实执行"的组合方案对服务端是有效的——不需要做 JSVMP opcode 级逆向。

**send-email / verify-email 也已用真实邮箱联调通过**（18356966159@163.com，用户提供）：

1. OCR 裁剪 padding 从 4 调到 12 后识别成功率明显提升（多组真实数据对比见下方"OCR padding
   调优"小节），验证码提交 `errorCode:"0"` 成功率稳定。
2. `send_email_code()` 用真实邮箱触发，返回 `{"expiresIn":300}`，用户真实收到邮件验证码
   `196598`。
3. `verify_email_code()` 用这个真实验证码调用，返回 **HTTP 204 No Content（空body）**——
   这是之前没抓到过的"验证码正确"响应形态（之前只抓到过错误码 `400 CodeNotExist`）。
   代码里最初写的 `resp.json()` 在 204 空body上会抛异常，已修复为按状态码判断。
4. **交叉验证**：用一个故意错误的验证码 `000000` 重新调用 `verify_email_code`，
   返回 `400 {"error":"CodeNotExist"}`——证明 204 vs 400 的区分是真实生效的判断逻辑，
   不是巧合返回。
5. **额外发现**：`verify-email` 不需要和 `send-email` 用同一个 CAS session/cookie
   （两次调用用的是全新建立的 `get_cas_session()`，验证码校验是按邮箱+验证码的
   pair 在服务端校验的，不绑定到发起 session），这点跟最初假设"两步要共用session"
   不一致，属于实测澄清的细节。

### OCR padding 调优（实测对比，4组真实验证码图片）

| 目标字 | pad=0 命中 | pad=4 命中 | pad=8 命中 | pad=12 命中 |
|---|---|---|---|---|
| 猜/阿/薄 | 2/3 | 2/3 | 3/3 | 3/3 |
| 隘/倍/迟 | 1/3 | 2/3 | 3/3 | 3/3 |
| 逞/斑/彻 | 0/3 | 1/3 | 3/3 | 3/3 |
| 齿/邦/跋 | 2/3 | 2/3 | 2/3 | 2/3 |

裁剪太紧（pad=0/4）会把分类模型依赖的笔画边缘上下文切掉，pad=12 是目前用的值
（`recognize.py`），综合命中率明显更好，但不是100%（第4组 pad=12 也只有2/3）——
`captcha_client.py` 的 `solve_and_verify()` 靠"识别不全就换新挑战重试"（max_attempts=6）
兜底，不追求单张图片100%准。

## 补充：真正完成登录的接口（2026-07-29，比 verify-email 更靠后一步）

之前一直以为 `sms/code/verify-email` 返回 204 就是"登录成功"，但用户走了一遍真实浏览器
的完整登录（邮箱验证码登录）之后发现，后面还有一个独立的接口才会真正让 Keycloak 完成
登录、在 `www.pkulaw.com` 域下种下正式的登录态（`pkulaw_v6_sessionid`、
`access_token` 等）：

```
POST https://cas.pkulaw.com/auth/realms/fabao/login-actions/authenticate
     ?session_code=...&execution=...&client_id=pkulaw&tab_id=...
body: email=xxx%40Gmail.com&loginType=5&tabType=emailValidate&source=&emailPrefix=xxx&emailSuffix=&emailCode=862274
```

`session_code`/`execution`/`tab_id` 这三个值**就在最初那个
`GET .../protocol/openid-connect/auth` 返回的登录表单 HTML 里**（`get_cas_session()`
已经在发这个请求了，不用多发一次），登录页面其实是好几个 tab（手机/邮箱/微信...）的表单
堆在一起，每个 tab 一个 `<form id="kc-form-loginN">`，邮箱 tab 是
`id="kc-form-login5"`（`loginType=5` 对应），action URL 里带着这三个参数，所有 tab
共用同一组值。表单字段：
```html
<input type="hidden" name="email">
<input name="loginType" value="5" type="hidden">
<input name="tabType" value="emailValidate" type="hidden">
<input name="source" value="" type="hidden">
<input type="text" name="emailPrefix">
<div class="select-items">...gmail.com/qq.com/hotmail.com/icloud.com 是预置后缀，
    选"其他"才会用到 name="emailSuffix" 这个输入框...</div>
<input type="text" name="emailCode">
```
`email` 字段是完整地址（`emailPrefix@域名`），`emailSuffix` 只有邮箱后缀不在预置的
gmail/qq/hotmail/icloud 四个之一时才会有值（页面提示"其他邮箱注册时需待人工审核"，
这条路径没有实测过）。

**这里最初的假设是错的**：以为 `login-actions/authenticate` 提交成功后就是一串纯
服务端 302 能自动跟完，实测发现只对了一半——`requests` 确实能自动跟到第一跳
`static.pkulaw.com/statics/kc/index.html?redirect_path=...&code=...`，但到这里就
不会自己继续跳了，因为**这一跳之后是靠这个中转页自己的 JS 决定下一步去哪**：

```js
if (getQueryVariable('redirect_path')) {
    window.location.href = getQueryVariable('redirect_path') + '?code=' + getQueryVariable('code')
}
```

按这段 JS 字面意思拼出来的 URL 是 `redirect_path + '?code=' + code`，但 `redirect_path`
本身已经带了 `?way=topGuid`，字面拼接会拼出两个问号的非法 URL（跟真实抓包里那条被中止的
`reqid=262 GET .../case?way?code=...` 对上了）。真正跑通、也是真实浏览器最终成功落地
的形态，是从 `请求链路.md` 最开始记录的完整链路里对照出来的：`reqid=263` 用的是
`redirect_path + '&code=' + code`（用 `&` 不是 `?`）。所以 `complete_login()` 里是
手动解析这一跳返回的 `redirect_path`/`code`，按 `&` 拼出正确 URL 再手动发一次 GET，
不是靠 `requests` 自动跟完的。

**已用真实账号完整验证通过**（hj1558109546@gmail.com，网站预设白名单邮箱后缀之一）：
两跳走完之后，`session.cookies` 里出现了 `pkulaw_v6_sessionid`、`authormes`、
`LoginAccount`、`userislogincookie` 这些正式登录态 cookie（`authormes` 的值和之前
真实浏览器登录后抓到的完全一致），`is_logged_in()` 返回 `True`。

**同时验证了网站自己的限制**：163.com 这类不在预设白名单（gmail/qq/hotmail/icloud）
里的邮箱后缀，`complete_login()` 提交后不会跳到中转页，登录不成功（网站提示"其他邮箱
注册时需待人工审核"）——这是网站自己的业务限制，不是代码问题，`complete_login()` 里
已经加了这种情况的报错提示。

全部实现在 `captcha_client.py` 的 `complete_login()`，配合 `get_cas_session()` 现在
返回 `(session, login_ctx)`。判断是否真登录成功用 `is_logged_in()`：拿同一个 session
请求 `www.pkulaw.com` 任意页面，看响应头 `islogin` 是不是 `"1"`（这个响应头之前分析
文章页面时就确认过是真实可靠的登录态标记）。

## 补充：EdgeOne（腾讯云 CDN/WAF）的 JS Cookie 挑战（2026-07-29）

除了登录本身，`www.pkulaw.com` 偶尔会对页面请求返回一个"假页面"——响应体不是真实内容，

站点之前 `demo.py` 里（用户自己手动登录时抓到的真实 cookie）出现过的
`'__tst_status': '538622729#'` 完全一致——`__tst_status` 这个值看起来是这批
WAF 脚本部署期间的固定常量（同一批部署反复出现同一个值），`EO_Bot_Ssid` 才是每次
挑战都不同的随机值。

已实现 `eo_challenge.py`：`is_challenge_page(resp)` 判断响应是不是这种挑战页（页面短
且含 `EO_Bot_Ssid` 字符串），`solve(html)` 跑沙箱拿到 cookie dict，
`get_with_challenge_retry(session, url, ...)` 是个直接替代 `session.get` 的封装，
撞上挑战会自动解一次再重试。

**实测情况**：用真实登录后的 cookie 请求文章页，大多数情况下直接 200 拿到完整正文
（没有撞上这个挑战），说明这个 WAF 挑战不是每次请求都触发，具体触发条件（请求频率？
IP 信誉？特定 header 缺失？）还没有摸清楚——目前的应对策略是"撞上了就自动解"，不是
"每次都主动先解一遍"，跟 wkinfo 项目对 G_* 风控信号的态度一致：先有能力应对，具体
触发阈值留给后续观察。

## 引擎判断

- **主要卡点**：`collect`/`eks` 两个字段怎么生成——写入点确实在 tdc.js 里，但 tdc.js 本身是
  JSVMP 字节码，不是"找到一个函数看懂逻辑"就能解决的，需要先做字节码层面的还原（recover 阶段）。
- **好消息**：`pow_answer`/`pow_calc_time` 已经完全搞清楚了，是标准 MD5 碰撞爆破，跟 tdc.js 无关，
  纯 Python 可解，不需要等 tdc.js 还原完成。
- **好消息2**：`ans`（点击坐标）是图像识别问题，跟 wkinfo 项目里 clickWord 的套路一致，不涉及
  JSVMP，可以独立实现。
- 下一步（`recover` 阶段）：对 tdc.js 的 `__TENCENT_CHAOS_VM` 字节码解释器做还原，目标是搞清楚
  `collect`/`eks` 两个值分别由哪些"指令"生成、依赖哪些运行时环境值（canvas/font/mouse轨迹/时间戳等），
  评估是"纯算法可还原"还是"必须真实执行这段字节码（用 Node 起一个沙箱解释器来跑）"。后者也仍然满足
  "不依赖浏览器/不补环境"的要求——只要能在 Node 里独立执行这段 VM 字节码而不需要真实 DOM/浏览器 API。
