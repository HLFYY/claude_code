# 请求链路记录：law.wkinfo.com.cn 滑块验证码 (blockPuzzle)

## 目标
- 页面: https://law.wkinfo.com.cn/trial
- 数据接口: https://law.wkinfo.com.cn/csi/captcha/check
- 加密参数: pointJson, token
- 目标: 纯 Node.js 算法还原，脱离浏览器/补环境

## 请求链路 (已用 chrome/js-reverse-mcp 抓包验证 + Node.js 复现验证)

1. `POST /csi/captcha/get`
   - body: `{"captchaVO":{"captchaType":"blockPuzzle"}}`
   - resp.repData: `secretKey`(16字符,用作AES-128 key), `token`(32位hex,校验凭证),
     `originalImageBase64`(背景图,含1个真缺口+2个干扰假缺口), `jigsawImageBase64`(拼图小块,47x155,真实缺口位置的裁块)

2. 前端拖动滑块 -> 计算 x 偏移 -> AES 加密:
   - `pointJson = AES-128-ECB/PKCS7(JSON.stringify({x, y:5.0}), key=secretKey)` , base64
   - `captchaVerification = AES(...)(token + '---' + JSON.stringify({x,y}), secretKey)` (仅在 check 通过后, 提交 /csi/captcha/verify 时使用, 本次目标未要求)

3. `POST /csi/captcha/check`
   - body: `{"captchaVO":{"captchaType":"blockPuzzle","pointJson":<enc>,"token":<token>}}`
   - resp: `repCode:"0000"`, `repData.result:true|false`

## 加密算法来源 (源码定位, 非猜测)
- `assets/js/verify-slipping/ase.js`:
  ```js
  function aesEncrypt(word, keyWord) {
    let key = CryptoJS.enc.Utf8.parse(keyWord);
    let srcs = CryptoJS.enc.Utf8.parse(word);
    let encrypted = CryptoJS.AES.encrypt(srcs, key, {mode: CryptoJS.mode.ECB, padding: CryptoJS.pad.Pkcs7});
    return encrypted.toString();
  }
  ```
  => AES-128-ECB, key = UTF8(secretKey) 原始字节 (16字符=16字节), PKCS7 padding, 无 IV (ECB), 输出 Base64。

- `assets/js/verify-slipping/verify.js` (Slide.prototype.end / refresh):
  - `token` 直接来自 `res.repData.token` (captcha/get 响应), 原样透传, 无需二次处理。
  - `pointJson` 明文为 `{"x": moveLeftDistance, "y": 5.0}`。

## 验证 (equivalence proof)
- 用真实抓包样本核对: secretKey=`VkLeMO2auT0ISZ9V`, 密文=`kzW4RCfnQ/x1/E9CgHaG5nXBAy6h5c5sLta+tcp51Y0=`
  -> Node `crypto` (aes-128-ecb) 解密得到 `{"x":111.6,"y":5}`，且用同一明文重新加密与原密文逐字节一致。
- 用同一份 Node.js 实现 (`crypto.createCipheriv('aes-128-ecb', key, null)`, PKCS7 autoPadding) 完整走一遍
  `get -> 缺口识别 -> encrypt -> check` 的真实网络请求 (无浏览器/补环境), 连续 5 次全部返回 `"result":true`。

## 缺口识别 (gap detection, 非加密但为“顺利访问接口”所必需)
- 背景图里有 1 个真缺口 + 2 个干扰假缺口(反自动化措施)。单纯边缘计数会被假缺口误导 (实测选中干扰缺口, check 返回 `repCode:6111 验证失败`, 说明加密格式本身是对的, 只是坐标错)。
- 改用"滑块小图 vs 背景图"逐列灰度相关系数扫描 (Pearson correlation, 限定在拼图小块的不透明 mask 内): 真缺口相关系数显著更高(~0.9+), 干扰缺口普遍 ~0.4-0.6, 区分度非常明显。
- 实测连续 5 次实时请求, 该方法定位的 x 全部通过 check (`result:true`)。

## v3: clickWord 类型 + 识别全部移至 Python (ddddocr), Node 只做加密
- `captchaType: "clickWord"` (点选文字) 与 blockPuzzle 共用同一套 get/check/verify 接口和 AES 算法，区别只在于:
  - `captcha/get` 响应里 `wordList` 是按顺序要点击的汉字 (如 `["哥","天","系"]"`), 没有 `jigsawImageBase64`
  - `pointJson` 明文是坐标数组 `[{"x":..,"y":..}, ...]` (对应 wordList 顺序), 而不是单点 `{"x":..,"y":..}`
  - `verify.js` 里 `Points.prototype` 对应这个类型, 逻辑和 `Slide.prototype` 平行, 加密方式完全一致
- 识别部分改用 **ddddocr** (Python 库), Node 只保留 `aes_encrypt.js`(纯加密, 无识别逻辑):
  - blockPuzzle 缺口: `ddddocr.slide_match(piece, bg, simple_target=True)`。实测 `simple_target=True` 8/8 通过, `simple_target=False`(默认, 先裁剪透明边) 只有 6/8 —— 说明该网站的缺口图不能裁边, 裁边反而丢失了匹配需要的上下文。
  - clickWord 点选: `ddddocr.detection()` 找字符框(稳定), 但默认/old/beta 三个分类模型单独识别这种"旋转+彩色+自然照片背景"的汉字准确率都不高(单模型整单验证码全对的概率 0~33%)。改成三个模型的识别结果取并集(+裁剪时四周各留4px），整单命中率提到 60%。由于重新拉取一次验证码是免费的，`solve()` 采用"识别不confident或校验失败就换一张重试"策略(默认 `max_attempts=6`)，而不是死磕单张图片的识别精度。
- 实测: blockPuzzle / clickWord 各连续 3 轮完整 `get -> recognize(Python/ddddocr) -> check -> verify`, 6/6 全部 `check.result:true` 且 `verify.repCode:"0000"`。
- 运行环境: 需要 `/Users/houjie/venv/python3-forcrawl/bin/python` (已装 ddddocr/opencv/numpy)。

## v4: Python 实现完整注册链路 (get -> check -> verify -> 发短信 -> 提交注册)
- `captcha_client.py` 新增 `request_sms_code()` (`GET /csi/user/captcha`) 和 `register()` (`POST /csi/user`), 以及编排方法
  `full_registration_flow()`，把 v3 的 `solve_and_verify` 延伸到真正的注册提交。
- **踩坑**: 一开始给 `/csi/user/captcha` 和 `/csi/user` 用了"更贴近真实浏览器"的一套 header
  (`identification`/`module`/`ucv`/`appversion`，模拟 Angular 拦截器加的那套)，结果 `/csi/user/captcha`
  直接返回 `{"code":"E_000_003","message":"注册验证码校验失败"}` —— 一开始怀疑是手机号用太多次被风控，换新手机号依然复现。
  最后发现只要把这两个接口也换成跟 `captcha/get|check|verify` 一样的极简 header 集合（`verify.js` 原生 `$.ajax` 用的那套），
  就完全正常返回 `{"id":...,"isConfirmed":true,...}`。即：更像浏览器的 header 集合反而触发了服务端更严格/不同的校验路径,
  统一用简单 header 反而更稳。没有再深挖具体是哪个字段导致的，因为已经找到可靠可用的方案。
- 实测 blockPuzzle / clickWord 各跑一次完整 `full_registration_flow` (随机手机号+邮箱, 避免复用旧数据), 两次都到达最终提交,
  返回 `{"code":"E_035_003","message":"手机验证码错误"}` —— 按约定这是"成功"信号 (说明全链路校验通过, 只有手工填的假短信码被拒)。

## 结论 (v1, Node.js 单栈实现)
- pointJson/token 完全由确定性算法生成, 无需浏览器环境、无需补环境, 纯 Node.js (`crypto` + `pngjs`) 可稳定复现并通过服务端校验。

## v2: Python 编排 + Node 只做缺口识别 (固定目录, 已实测)
- 目录: `wkinfo_captcha/`
  - `gap_detect.js` — 复杂部分(像素相关系数缺口识别), Node + pngjs, 以子进程形式被 Python 调用 (stdin/stdout JSON)。
  - `captcha_client.py` — 简单部分(AES-128-ECB/PKCS7)用 Python (`pycryptodome`) 实现 + 完整 HTTP 编排 (`get -> check -> verify`)。
- **踩坑记录**: Python `json.dumps({"y": 5.0})` 输出 `"y": 5.0`（带空格, 保留 `.0`), 而 JS `JSON.stringify({y:5.0})` 输出 `"y":5`（无空格, 整数省略 `.0`)。
  这个明文格式差异直接导致服务端 `com.anji.captcha.service.impl.BlockPuzzleCaptchaServiceImpl.check` 抛 `NullPointerException` (500), 而不是正常的"验证失败"业务错误码 —
  说明服务端对解密后 JSON 明文的格式有隐性依赖 (可能做了非标准的字符串层面处理而非纯 JSON 解析)。
  修复: Python 侧手写紧凑 JSON 序列化 (`point_plaintext()`), 整数浮点数一律去掉 `.0`, 不留空格, 与 JS `JSON.stringify` 字节级一致。
- 修复后连续实测 3 次完整链路 (`get -> gap_detect(Node) -> check -> verify`), 全部 `check.result:true` 且 `verify.repCode:"0000", repMsg:"成功"`, 与真实浏览器抓包的 `/csi/captcha/verify` 响应完全一致。
- 该项目确认是开源 **AJ-Captcha** (anji-plus/captcha) 的定制部署 (`com.kland.csi.api.captchaSlipping...` 为业务方包名, `com.anji.captcha...` 为开源库包名)。
