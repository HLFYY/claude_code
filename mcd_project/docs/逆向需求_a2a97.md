## 一、实验方法
对 ACTIVE 模板 `device_templates/shortbox_STK-AL00_20261022.json`(29 字段),**逐字段改成一个不同的合法值 → `make_box` 重新打包+重新签名 → POST `fp-it.fengkongcloud.com/deviceprofile/v4` 注册 → 看 code**。
- `code=1100` = 注册期**不校验**该字段(可自由伪造)
- `code=1902` = 注册期**校验/拒绝**
脚本:`scratchpad/exp_field_validate.py`,直连本机 IP(注册不需要代理)。

## 三、由此确定的三件事
1. **加密外壳(`make_box`:data/ep/tn)已完全自洽、不是拦截点。** 任意改字段后重打包都能注册——`tn` 是对明文 JSON 的 RSA-OAEP 本地签名,每次重算即可,服务端无额外 client 秘密需求。
2. **注册期几乎不校验设备身份。** 唯一的门是 `a1`(采集模式枚举,必须是已知值如 "all"/"";不是加密字段)。连 a2/a97 随机都能注册成功并拿到**全新 deviceId**。→ **d 的唯一性本来就不是问题**(每次注册服务端新发 smid)。
3. **"同一设备 / 换机仍异常 / 706070" 不在注册期、不是某个没伪造对的加密字段。** 它发生在**发码/风控期**,服务端对 **a2/a97** 这个 token 做"是否数美真签"的校验:
   - 历史实测:原样复制**真实** a2 → 发码 420(过);**随机** a2 → 706070(挂)。
   - 本次补充:随机 a2 **注册照样 1100**。→ 注册放行、风控才查。

## 四、需要大佬确认的核心问题(THE 逆向目标)
**a2/a97 到底怎么来的?**(a2==a97==a126 去掉"B"前缀,同一 token;每次注册唯一)

- 它是 **libsmsdk.so 里客户端本地算出来的**,还是**某个服务端接口下发的**?
- 若**客户端可算**:算法输入是什么(seed / 设备字段 / 时间 / organization `qvdTr7A9k1DIU04ha4eP` / 内置 key)?在哪个 native 偏移?
  → 逆出来 = 能本地无限造**各自唯一且"真签"**的 token = 真正独立的设备 = 解决批量 706070。
- 若**服务端下发**:在哪一步的响应里(注册响应 `detail` 没有;是不是另有一次预热/握手调用)?
  → 那每台真机/云手机每次注册只能收一个,采集速率=瓶颈(当前天花板)。
