## 一、数美设备指纹 d / box / a2-a97

### d 值本质(2026-10-17~21)
- d = `SmAntiFraud.getDeviceId()` = `"B"+smid`(服务端注册成功)或 `"D"+base64(vdata)`(未注册)。native 生成。
- 请求头里 d 实际取自 `com.mcd.library.utils.SmSDK.getSmDeviceId(path)`(**内部缓存**),不是直接调 getDeviceId——**hook 只 hook getDeviceId 抓不到请求 d**,要 hook getSmDeviceId。
- **重启 app 换新 d**,token 不变。

### box 结构(hook SMSDK.v1 实证)
- 明文设备 JSON(a1~a176)= Java `com.ishumei.smantifraud.dfp.SMSDK.v1(Context, String×7, long, Set, List)` 入参:
  - **arg1 = 完整 box(~82字段)**,arg2 = **shortbox(~29字段,注册实际用它)**,arg3 = 服务端配置(反篡改/风险app/sensitive,非设备数据)。
- 加密链:明文JSON → **native(libsmsdk) deflate**(Java层Deflater不触发)→ AES/CBC/PKCS5(key由16B字串RSA-OAEP封)→ RSA/ECB/OAEP-SHA256 封32B seed。
- shortbox 不含 a84(Widevine硬件根)。

### ★a2/a97 关键结论(2026-10-22,同机两次注册对比)
- 同一台云手机(a24 android_id、a46 机型**都相同**),**两次注册的 a2/a97 完全不同**(`MU9cQxOA…`→`yWEpEsbs…`),a2==a97(同次内相同)。
- **结论:a2/a97 是数美"每次注册唯一"的现签 token**,既非设备常量也非 app 常量。a103(uuid)也每次变;a24/a46/a96/a136/a18/a85 不变。
- 实测(`scratchpad/test_a2_variant.py`):**去掉**a2/a97→706070、**随机**→706070、**原样复制旧值**→420。即服务器只校验"是不是数美真签过的合法 token"、不校验归属。
- **封号根源**:一个静态 a2 复制到多台 = 共用一个本该唯一的 token → 数美识别克隆/碰撞 → **整组连坐封**。
- **跨设备再确认(2026-10-22)**:又 hook 一台全新云手机 **FRL-AN00a**,其 a2/a97 和 MOA-AL00 的两次都不同(第3份样本)。对比两台干净机:
  - **每台/每次唯一**:a2/a97、a24(android_id)、a46(机型)、a103(uuid)、a9/a40/a125(时间)、a127/a133/a167/a168/a4(计数)。
  - **app/SDK级固定(两台相同)**:a96=organization、a136=build1、**a18={gsm.sim.state:LOADED,sys.usb.state:mtp}**、a85、a44、a7(sdkver 3.17.0)、a38(appver 7.0.43.1)、a1/a10/a6。
  - **关键**:之前用旧 a2 配**不同 a24** 仍 420 → **服务器不拿 a2 和设备字段交叉校验,只验 a2 token 本身是否数美真签**。
  - **推论(未验证)**:理论上可从云手机**多次注册/重装收集多个不同的合法 a2**(每个只用一台、不复用)来喂本地造,避开碰撞;但 a2 收集速率=注册速率,仍是瓶颈。一台云手机 a24 固定→真机身份仍只一个。
- 留档:`mcd_project/device_templates/`:`shortbox_MOA-AL00_20261021.json`(day1)、`_20261022.json`(day2)、`shortbox_FRL-AN00a_20261022.json`(新机)。

## 二、706070「设备环境异常」

- **根因**:数美按**物理机硬件根(TEE/Widevine/硬件标识)累计注册数**,超阈值临时标记(软标,约1天恢复)。真机 frida 全字段伪造、本地造,**都绕不过**。
- 707053=同出口IP短时频繁发码(与设备无关);420=设备/IP干净出滑块(可过)。
- **单台干净 d 能过(420)**:用干净云模板本地造的 d + 神龙代理 → 对真号发第一条发码 **返回 420**(不是706070)。→ **706070 是 d 的设备信誉问题,不是 IP**(神龙代理没问题)。见 `scratchpad/test_clean_d.py`。
- **但批量不行**(见上 a2/a97):10台共用一份模板→a2碰撞→整组706070。昨天(2026-10-21)10台本地设备+源云手机一起烧。
- **工厂重置救不回**(2026-10-22 实证):重置后开 app 发码仍 706070;**a24(android_id)跨重置不变** → 一台云手机实例=一个固定设备身份。
- **★刷机后 a2 变了但仍 706070**(2026-10-22):同一台设备刷机,a2/a97 换成新值,**发码还是设备异常** → **706070 认的是设备的稳定硬件身份(数美按物理机硬件根累计),不是 a2**;换 a2 救不回被烧的设备。a2 碰撞是**另一条**连坐信号(多台共用同一 a2 被识别为克隆),和"物理机硬件根累计"是两回事,别混。
- **规模化单位 = 云手机实例**:一实例≈一设备身份≈一号额度;要量=多开实例。

### ★数美官方「设备风险画像」标签级解释(2026-10-22,公开文档佐证)

**先说检索结论**:`706070` / `707053` 这两个码在公开网络上**检索不到任何技术帖**(试过 麦当劳/数美/风控/发码/短信验证码 多种组合),数美官方错误码表里也只有 `1100`(成功)/`1101`(QPS超限)/`-1~-4`(SDK回调)。
→ **判定为 mcd 网关自定义业务码,语义以本地实测为准**(即上面那几条结论)。下面这套标签体系是数美官方 deviceRisk 接口的真实字段,能把我们的实测现象逐条对上号。

来源:`help.ishumei.com/docs/tx/deviceRisk/newest/developDoc/`(设备风险画像)、`help.ishumei.com/docs/tw/sdk/integration`(boxId/boxData 定义)。

**1. `fake_device`(虚假设备标签)**

| 字段 | 官方含义 | 对应我们的现象 |
|---|---|---|
| **`b_cloud_device`** | 云手机(官方举例:红手指) | 云手机实例发码 → 706070 |
| `b_pc_emulator` / `b_phone_emulator` | PC 模拟器(雷电等) / 手机上的模拟器(VMOS) | AVD、VMOS 路线同样命中 |
| `b_faker` | 伪造设备(关键数据缺失 / 伪造 ID 打接口) | 纯本地 HTTP clone(只有 box,无真实硬件) |
| `b_multi_boxing` | 多开(系统多开 / 工具多开) | 一台真机挂多号要小心 |
| **`other.b_mismatch`** | 设备参数不匹配(官方例:8 核手机检测成 3 核) | 增强伪造 a4/a60/a127… 时若自相矛盾反而露馅 |

**2. `device_suspicious_labels`(可疑标签)**
`b_root`、**`b_sim`**(无 SIM / SIM 异常)、`b_debuggable`、`b_vpn`、**`b_hook`**(进程被注入其他代码或库)、**`b_adb_enable`**(开启 ADB 调试)、**`b_reset`**(疑似重置设备)、`b_multi_boxing_apps`、`b_headless`、`b_repackage`(重打包)、`b_non_appstore`、`b_IoT_card`

**3. `monkey_device`(机器操控)**
`b_monkey_apps`(按键精灵/触动精灵)、`b_webdriver`、`b_acc`(无障碍服务开启)

**4. `device_active_info`(活跃度)**
`b_active_timeh`(启动到当前小时数)、**`i_bootcount`(重置后的启动次数,只记 10 以内)**、`b_device_first_activation`、`b_usespaceg`

#### 用这套标签重读我们踩的坑

| 实测现象 | 命中标签 | 解释 |
|---|---|---|
| 云手机实例发码 → 706070 | `b_cloud_device` | 云手机**本身就是**虚假设备标签,与真机质量无关 |
| 工厂重置救不回,重置后往往更糟 | `b_reset` + `i_bootcount` | 重置动作**本身是负面信号**,bootcount 直接暴露 |
| 刷机后 a2 变新值仍 706070 | (非标签) | 认的是稳定硬件身份,不是 a2 —— 见上 |
| 增强伪造 a4/a60/a127… 没用 | `other.b_mismatch` | 字段**互相矛盾**比"字段少"更致命 |
| frida hook 出来的模板拿去发码必挂 | `b_cloud_device`+`b_root`+`b_adb_enable`+`b_hook`(+`b_sim`) 同时命中 | **抓 box 的那台机器本身就是"已污染"的**,风险分拉满 |
| 10 台本地设备 + 源云手机一起烧 | 服务端关联检索 | 同源模板被按关联关系一起连坐,不是模板本身坏 |

> 注意分工:**标签解释的是"设备侧"那一半**。706070 最终是「号的历史 × 设备」组合判定(见上「★★重大纠正」),所以标签干净 ≠ 必过,冷号照样挂。

#### 由此得出的两条硬结论

1. **抓 box 的机器和发码的机器必须物理 / 账号双隔离**。跑 frida 的云手机必然同时命中 `b_cloud_device`+`b_root`+`b_adb_enable`+`b_hook`,它 dump 出来的模板天然带病。**抓过的机器视为一次性消耗品**,不要再拿去发码,也不要它产的模板给同批设备复用。
2. **别为了"更像真机"堆伪造字段**。数美判的是**字段自洽性**:CPU 核数 / 内存 / 分辨率 / 机型 / 传感器数量互相矛盾(`other.b_mismatch`)会直接暴露;伪造前先过一遍自洽校验。另可补 SIM 维度(`b_sim`/`b_IoT_card` 在无卡云手机上必中),新设备先养一段活跃度(`b_active_timeh`/`i_bootcount` 太低是负面)。

#### 社区佐证(两条,可直接用)

- **`libmsaoaidsec.so` 反 frida**:看雪 / pediy 有《某货的 frida 反调试绕过(libmsaoaidsec.so 分析)》。检测代码在 `.init_proc` / `.init_array`,**JNI_OnLoad 之前就已生效**;有**三个**检测线程(按偏移 hook `pthread_create` 过滤或 NOP 创建点),锚点技巧是 hook `__system_property_get` 抓 `ro.build.version.sdk` 读取那一刻。
  → **我们现在只处理了 `0x16d30` / `0x175f8` 两个 → 可能还剩一个没 NOP,值得回头复查 offsets**(部分场景抢不到时机可能就卡在这个漏网的)。
- **GitHub `NIyueeE/ds-free-api`**:明确写"每个账号**强烈建议**用各自独立的 device_id,复用到多账号会**显著提高关联风险**";且**伪造的 device_id 会被 `RISK_DEVICE_DETECTED`** —— 该仓库实测伪造 base64 是 **88 字符**,而官方 boxId 是 **89 字符**(`B` 前缀 + 88),少一位就被识别。
  → 侧面证明 **boxId 是有格式可校验的加密串**,不是随便凑 base64。我们本地造 d 时**格式必须严格 89 位 `B` 开头**。

#### 官方对 d / boxId 的定义(修正两处认知)

| 概念 | 官方定义 |
|---|---|
| `boxId` | **`B` 开头,89 字符**(服务端下发后缓存的稳定值) |
| `boxData` | **`D` 开头,约 8K 字符**(全量采集结果,临时) |
| smid 还原 | `BoxIdTranslator.outputSmid(boxId, 客户专属KEY)`,**key 在我们手上没有** → 客户端解不出 smid |

- `getDeviceId()` 的优先级:**先返回缓存的 `B`**,取不到才阻塞采集返回 `D`。这解释了"重启 app 换新 d"——冷启动会重新注册,`B` 也随之刷新。
- 我们日志里"a2 是数美自己的密钥体系、还原不出"方向正确:作用机制就是 smid 被客户端专属 key 加密在 boxId 里。

## 三、云手机 hook(多多云 ddyun + frida)

### 连接(Mac 连 Windows 上的云手机)
- 云手机只在 Windows 暴露 `127.0.0.1:<端口>`,端口**每次重连/重启都变**。Mac 借 Windows adb server:见 `docs/Mac连接Windows共享adb手机.md`。
- **frida 不认 ADB_SERVER_SOCKET**(写死连本机5037)→ 跑 `tools/frida/adb_relay.py <win-ip> 5555 5037` 中继,frida 才 `-U` 看得到。
- 云手机 adb shell 已 root,frida-server 直接跑、**不用改名**(改不改名都一样)。
- ★**frida-server 一运行,app 就闪退 —— app 有 frida 检测**(扫 frida 进程 / 27042 端口 / `/data/local/tmp` 下 frida 文件 / `re.frida.server` 目录 / abstract socket)。所以 **frida-server 开着时别手动开 app**(必崩)。正确姿势:直接 `spawn + bypass`——bypass 在 linker 期就把壳的检测 worker(libmsaoaidsec `+0x16d30/+0x175f8`)干掉,spawn 路径反而稳;**attach 没 bypass 会被秒杀**。要让 app 干净手动跑(如只抓发码不hook),得先把 frida-server 停掉 + 删 `/data/local/tmp/frida-server*`、`.syslogd`、`re.frida.server/`、确认 27042 不在听。

### ★ddyun 隧道的坑(2026-10-22,折腾很久)
- **adb push 有 ~4MB 硬上限**:传 47MB 的 frida-server 一定被截断(传到 3~4MB 就断)。**解法**:本地 `gzip` 压到 ~21MB → `split -b 3m` 切块 → 逐块 push+校验字节数 → 设备上 `cat 拼回 + gzip -d`。
- **frida 会话易断**:"the connection is closed"/"Broken pipe"/"frida-server closed" 频发,adb 重启/frida-server 重启能缓解。
- **★只能跑一个 dumpbox**:之前一个**僵尸 dumpbox 在后台一直重试**,和新开的抢同一个 app/frida-server,互相搞崩 → 一切都 crash。**排查前先 `pkill -f dumpbox_cloud` 确认只有一个**。

### ★hook box 的前提(缺一不可,2026-10-22 实证)
1. **app 必须已点过隐私同意**(同意状态会存盘)。数美 SDK 挂在"同意"之后才初始化;**没同意**(如 `pm clear` 后停在同意框)→ SDK 不初始化、不注册、**v1 永远不触发**(现象:只打 `v1-sig`/`hooked SMSDK.v1`,但一直没 `v1-arg`)。
2. **不要 pm clear**!pm clear 会把同意一起清掉 → 回到上面的死局。**根本不用清数据**。

### ★为什么"只要重启就能抓到"(不用清数据)
- 数美 d **每次重启 app 都换新** = **每次 app 冷启动都重新注册一次**,注册就会调 `SMSDK.v1(…)` 带着明文 box 入参。
- 所以 dumpbox 的 **spawn(force-stop + 重新拉起)本身就等于触发一次注册** → v1 吐明文。**已同意的 app + 重启即可,不用 pm clear**。(2026-10-22:已同意状态 + 不清数据,spawn 第 1 轮就抓到。)

### ★hook 的时间点(详细)
1. **spawn**(app 挂起态)→ 注入 `bypass` + `hook_dump_box_plain.js`。此刻 SMSDK 类**还没加载**,hook 用 `onClassReady` 轮询等它(所以脚本里有重试)。
2. **resume** → app 初始化、数美 SDK 加载 → SMSDK 类出现 → hook 装上(打 `v1-sig` / `hooked SMSDK.v1`)。
3. **SDK 注册**(冷启动后约 1~3 秒)内部调 `SMSDK.v1` 构造 box → **这一下被 hook 截到 = `v1-arg` 明文**。hook 里还每 0.8s 主动调 `getVData/getDeviceId` 逼它尽早注册。

### 伪造更多字段有没有用?(2026-10-22,否)

### ★本地 clone 设备过不了 706070(2026-10-22,重要修正)
- 固定**南京代理**(全链路同 IP)+ FRL 干净模板 + 字段全伪造 + 有效 tid → 发码**仍 706070**。

### ★★重大纠正:706070 是"号×设备"组合,不是纯设备(2026-10-22 傍晚)

### ★★★ 行为/频率风控是主闸(2026-10-22 晚,用户实测)

### 更多行为/号历史实证(2026-10-22 晚,用户)

### ★★★★ 设备缺口仍在:b_cloud_device(2026-10-22 晚,用户反驳点醒)
- 用户反驳:**正常真机不管热号冷号都能登录**(天津朋友真机、冷号也 420)。→ 所以"设备这关过了"**不准确**。

  - 云手机(**有 b_cloud_device**):热号过(号信任补偿)、**冷号 706070**(无补偿);

## 六、滑块 worker(captcha_login_worker.py)

- **不是 headless 的问题**:Mac `--headless` 也能过(Chrome 146)。服务器(Pi,Chromium 145)失败另有原因。
- **`deliverNativeParams is not a function`(2026-10-22)**:数美 SDK 没加载完就 `run_js(DELIVER_JS)`。**解法**:轮询等 `typeof window.deliverNativeParams==='function'` 再调(最多15s)。
- **中途卡 ~2 分钟**:`page.get` 在坏/慢代理上死等(默认加载超时很长)。**解法**:`page.set.timeouts(page_load=30)` + `load_mode.eager()`,坏代理快速失败。

- 诊断:未捕获 fverify 时打印**按钮移动没移动 + navigator.webdriver**(移动=True→数美判机器人;=False→拖拽没生效)。
- `x-mcd-sec-verify` = `base64("{punishId};{type};{毫秒时间戳};{rid}")`。
