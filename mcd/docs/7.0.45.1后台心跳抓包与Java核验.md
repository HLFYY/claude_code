完整目录：`../tools/mitm/cap_20261128_2030_ADB三轮后台对照日志/`。

每轮均先 force-stop APP，再开始独立抓包，启动 APP、点击“我的”、返回桌面，
随后由 ADB 控制并监测屏幕；没有在基线实验中启动 Frida。

| 编号 | 原始抓包 | 正式后台观察 | 结果 |

| 1 | `1-后台保持亮屏10分钟-完整抓包.mitm` | 亮屏 10 分钟 | 后台 6 对；随后连接以 1006 异常断开，没有后台重连 |

HTTP flow 总数分别 93、80、115；全文件客户端 WS 消息分别 41、7、48 条，

三个文件的 SHA256 和屏幕采样记录见同目录分析及脱敏 JSON，离线回归重新校验了哈希。

结论边界：

- 后台息屏并不必然立即停止心跳；仅一轮亮屏异常不能说明亮屏导致断连。
- 正式后台区间没有新的 api/api2 业务 HTTP，不等于没有 WS 或 SDK 活动。
- `$AppEnd` 是退后台埋点，不是进程终止证明；友盟二进制上报未全面解码。
- 系统代理没有提供请求 UID，不能凭这些包判断 APP 是否读取其他应用。
- 实验有 USB/ADB 连接和充电影响，不能外推到拔线、深度 Doze 等场景。

## 2. Java 默认路径与协议

### WebSocket 握手

端点：`wss://ws.mcd.cn/bff/pulse/ws`。
`de.i`（SocketRequest.kt）读取 SecBox.getWskey()、当前账号 sid/meddyId、版本和场景。
sid 为空时返回 null，不建立连接。签名为：

```text
message = ct + meddyId + scene + sid + st + sv + v
sign = Base64_NO_WRAP(HMAC_SHA256(UTF8(wskey), UTF8(message)))
```

无分隔符。本次普通页面 ct="102"、scene=""、sv="v4"、v="7.0.45.1"。
wskey 使用返回字符串的 UTF-8 字节，不能先 Base64 解码，也不使用业务 token。
HTTP 的 Authorization / X-HMAC-DIGEST 是另一套签名，不能替代握手 sign。

`MCDTimeTable.getServerCorrectedTimeInMillis()` 为本机毫秒时间加偏移，偏移默认 0。
其更新函数使用响应 Date 与请求开始时间计算偏移，10 秒为校正判断阈值；
这不等于 Python 项目已经实现同样的自动校时。当前保活实现使用默认 0 的可配置偏移，
不新增校时请求，运维及限制见 `../../mcd_project/docs/7.0.45.1心跳实现与验证.md`。

### 心跳与后台断线

- `de.b` 构造 protobuf ClientMsgVO，type 为 HEARTBEAT_REQUEST。
- `de.f.p()` gzip 压缩后二进制发送；解压内容固定为 `42 11` 加 ASCII HEARTBEAT_REQUEST，19 字节；现有压缩包 39 字节。
- Config.heartbeatInterval 默认 15000 毫秒；客户端明确传给 HeartbeatManager，不能误用其独立构造默认的 30000。
- `de.c` 保留指令显示先 delay 再发送；三轮首发距握手约 15.695、15.479、17.003 秒。
- 服务端初始消息为 SYSTEM，不能把任意一次 recv 当作心跳确认；type 位于 protobuf 字段 8。
- `de.f.n(Throwable)` 的后台路径清理后返回；前台才可能按上限和退避策略重连。keepalive采用后台模型，失败停止；独立的pulse_guard保留其常驻重连实验策略，不声称等同真机后台行为。

同目录 `0-1-2-JADX-*.java` 保存了主要 WS 类的反编译证据。

## 3. 运行时密钥获取与验证

用户自行执行 `mcd/tools/frida/getd.sh hook_complete.js`，第 1 部分成功打印 SecBox
九个 getter 的值。SecBox 构造调用 init() -> JniLib0.cV()，Java 字段默认空串不等于
运行时值；JNI 初始化与 Java getter 能读取结果并不矛盾。

后续 HMAC 重载不匹配、拦截器 implementation 不存在、类 y 不存在，说明这些 Hook
目标未适配当前混淆代码，不能反推前面已成功输出的密钥无效。本次没有重新运行 Hook。

核验过程：

1. 先用已知 AES、signKey、HTTP v4 等有限候选试算，均未匹配；没有爆破。
2. 使用用户给出的运行时 wskey，按 Java 公式分别复算三轮握手，全部匹配。
3. 接入实际 `_pulse_headers()` 后，再用三份原始抓包回归，仍全部匹配。

业务和心跳实际使用的密钥保留在 `../../mcd_project/mcd_profiles.py`。
未使用的 sign_key、tmsk、ta_app_id、ta_sid、ta_sk 迁至同目录的
`mcd_profiles.local.json`，仅本地备份，不提交 Git；缺失或无效不影响现有功能。
本报告不复制明文。

| 字段 | 已核对用途/证据 |
| --- | --- |
| aesKey | SecurityUtils，AES/ECB/PKCS5Padding 加解密 |
| signKey | getter 直接交叉引用为 0，用途尚未确认 |
| v4ak / v4sk | qf.e 的 HTTP v4 访问标识 / HMAC 密钥 |
| wskey | de.i 的 WS 握手 HMAC 密钥 |
| tmsk | TencentSearch 的 mSecretKey，地图搜索、逆地理编码及路线规划 |
| taAppId / taSID / taSK | MCDASRManager 初始化腾讯 AAIClient 的语音应用 ID、凭证标识和签名密钥；taSID 不是登录 sid |

这是当前已验证构建的应用级配置，不是账号凭证；不能保证同版本不同构建、渠道、
热修复或后续初始化得到的值永远相同。旧版本配置保留，未知版本禁止回退混用。

## 4. 实现与验证状态

`../../mcd_project/keepalive.py` 已改为独立 WS 签名、共享版本配置、首发等待约 15 秒、
单调时钟限时、区分消息类型、统一 finally 清理及后台不重连；默认仍保持 180 秒异步会话。
HTTP 接口、队列、账号校验及 Redis 凭证更新逻辑不改。

随后先同步远端 c44df00（无冲突），发现其新加 pulse_guard.py 仍采用旧 token/st 签名，
经用户确认一并修复。新增 pulse_protocol.py 共享签名、消息解析和代理配置，两个入口
均使用已验证的 wskey；guard 保留常驻/退避重连，keepalive仍为限时/后台不重连。
共享模块不导入业务API或Redis，避免守护脚本为了复用签名间接加载整个业务客户端。

离线回归脚本在证据目录：`0-1-2-心跳实现离线回归.py`，共 50 项测试通过（原33项加守护17项）。
覆盖三份抓包完整性、三次签名、全部 96 条客户端消息及所有服务端消息的解析、
生命周期异常、代理、时间偏移和公共调用兼容性；新增守护签名、常驻重连/退避及只读凭据测试。
测试隔离 Redis/业务 API 并拦截出站连接。

尚未验证真实上游握手、代理链路和长期会话效果。离线匹配不等于上游接受；
心跳 ACK 也不能证明 sid 续期、账号恢复或设备风控解除。
