# 麦当劳 v4/v5 签名机制对比

## 一、双重签名架构

麦当劳 App 使用两套签名系统并存：

| 签名版本 | 算法 | 密钥来源 | HTTP Headers | 状态 |
|---------|------|----------|--------------|------|
| **v4** | HMAC-SHA256 | SecBox (麦当劳自己) | `authorization`, `X-Hmac-Digest`, `sv: v4` | 所有接口默认支持 |
| **v5** | TDRisk SDK | TrustDecision (第三方商业SDK) | `x-mcd-sign`, `sv: v5` | 渐进式部署，高风险接口 |

---

## 二、v4 签名（麦当劳自己的）

### 2.1 核心机制

```kotlin
// 1. 从 SecBox 获取密钥（JNI 调用 SO）
String v4ak = SecBox.INSTANCE.getV4ak();  // Access Key
String v4sk = SecBox.INSTANCE.getV4sk();  // Secret Key

// 2. 构建签名字符串
String authString = String.format(
    "%s\n%s\n%s\n%s",
    request.method(),           // GET/POST
    request.url().encodedPath(), // /bff/order/submit
    canonicalHeaders,           // ct;language;p;sid;...
    date                        // RFC1123 格式
);

// 3. HMAC-SHA256 签名
byte[] signature = hmacSha256(v4sk, authString);

// 4. 生成 Authorization Header
String authHeader = String.format(
    "hmac-auth-v1#%s#%s#hmac-sha256#%s#ct;language;p;sid;sv;token;v;x-mcd-gw-v",
    v4ak,
    base64(signature),
    date
);

// 5. Body 签名
byte[] bodySignature = hmacSha256(v4sk, bodyBytes);
String hmacDigest = base64(bodySignature);
```

### 2.2 当前状态

- ✅ 算法完全确认（标准 HMAC-SHA256）
- ✅ 实现代码已完成（`mcdonald_api_auth.py`）
- ❌ 密钥被某梆加固保护（等待脱壳）
- ⏳ 脱壳后 15 分钟可提取密钥并完成

### 2.3 能否模拟？

**答案：✅ 完全可以**

只需获得 `v4ak` 和 `v4sk` 两个密钥，即可完全独立模拟签名：
- 不依赖真实设备
- 不依赖 App 环境
- 不依赖服务端
- Python 纯代码实现

## 三、v5 签名（数美科技 TDRisk）

### 3.1 核心机制

```kotlin
// 1. 判断是否使用 v5（灰度算法）
if (DegradeManager.INSTANCE.shouldUseTdSign(request.method(), apiPath)) {

    // 2. 调用 TDRisk SDK
    TDAPISignResult result = TDRisk.sign(AppConfigLib.context, apiPath);

    if (result.code() == 0) {
        // 3. 获取签名（这就是用户说的 "D 参数"）
        String signature = result.signature();

        // 4. 使用 v5 签名
        request.addHeader("x-mcd-sign", signature);
        request.addHeader("sv", "v5");

        // 5. 移除 v4 Headers
        request.removeHeader("Authorization");
        request.removeHeader("X-HMAC-DIGEST");
    } else {
        // TDRisk 失败，降级到 v4
        return v4Sign(request);
    }
}
```

### 3.2 TDRisk 签名生成流程

```
1. 采集设备指纹（100+ 维度）
   ├─ 硬件参数：IMEI、MAC、AndroidID、序列号
   ├─ 传感器数据：加速度计、陀螺仪、磁力计
   ├─ 系统信息：屏幕参数、安装列表、文件列表
   └─ 行为特征：点击模式、滑动轨迹、输入速度

2. 生成 BlackBox（加密的设备特征包）
   TDDeviceInfo info = TDRisk.getDeviceInfo();
   String blackBox = info.getBlackBox();

3. 构建签名数据
   ├─ API 路径（"/bff/order/submit"）
   ├─ BlackBox（设备特征）
   ├─ 时间戳
   └─ 业务参数

4. 用数美服务端公钥加密
   （客户端只有公钥，私钥在数美服务器上）

5. Base64 编码输出
   ↓
   "Bwm8C/M8Y30Xv8wKFNhpcWCzZpyYwcrmqyHzutelLdfP10PVcNzjizN1UPC4lqGXdXdyedPcwrFoj/FI5zNc/g=="
```

### 3.3 渐进式部署

服务端配置文件控制：
```json
// https://img.mcd.cn/app/main/assets/requestConfig102.json
{
  "tdSignConfig": {
    "enabled": true,
    "rules": [
      {
        "method": "POST",
        "path": "/bff/order/**",
        "ratio": 50.0  // 50% 的设备使用 v5
      }
    ]
  }
}
```

灰度算法：
```kotlin
// 设备唯一 key（0-10000，持久化存储）
val deviceKey = getDeviceKey()

// 基于 key 稳定采样
return deviceKey < (rule.ratio * 100)  // 50.0 → 5000
```

**特点**：
- 同一设备选择稳定（不会来回切换）
- 服务端动态调整比例
- 支持通配符路径匹配
- 失败自动降级到 v4

## 四、v5 能否模拟？

### 4.1 答案：❌ 技术上可逆向，但无法独立模拟

### 4.2 四大障碍

#### 障碍 1：SO 文件独立且有保护

当前脱壳的是麦当劳 SO：
- `libcsiipowerenter.so` - 某梆加固（委托脱壳中）
- `libandjni.so` - 包含 SecBox 密钥

TDRisk 有自己的 SO：
```
lib/arm64-v8a/
├── libmobrisk.so          # TDRisk 核心库
├── libtrustdecision.so    # 或其他命名
```

**问题**：
- 麦当劳脱壳服务不包含 TDRisk SO
- TDRisk SDK 也有自己的保护（OLLVM、VMP、反调试）
- 需要单独再次委托脱壳（额外成本）

#### 障碍 2：依赖服务端密钥

```
v4 签名流程：
客户端完全独立
  → 只需 v4ak/v4sk
  → 纯本地计算
  → 可完全模拟 ✅

v5 签名流程：
客户端采集数据
  → 用服务端公钥加密
  → 发送到数美服务器
  → 服务端用私钥解密验证
  → 返回签名或风控评分
  → 无法绕过服务端 ❌
```

**关键点**：
- 客户端只有**公钥**（用于加密）
- **私钥**在数美服务器上
- 即使完全逆向出算法，也无法独立生成有效签名
- 必须和数美服务端交互

#### 障碍 3：设备指纹必须真实

TDRisk 采集的设备特征：
```
硬件层（无法模拟）：
- IMEI、MAC、序列号
- CPU 序列号、主板信息
- 传感器特征（陀螺仪漂移、磁力计偏差）

软件层（可模拟但会被检测）：
- 安装应用列表
- 文件系统特征
- 系统属性

行为层（极难模拟）：
- 触摸压力分布
- 滑动加速度曲线
- 输入节奏特征
```

**问题**：
- 模拟设备会被检测为"高风险"
- 签名验证可能通过，但风控评分极低
- 服务端仍会拒绝请求

#### 障碍 4：成本收益比极差

| 对比项 | v4 | v5 |
|--------|----|----|
| 逆向难度 | 中等（等脱壳） | 极高（需再次脱壳 + 分析商业SDK） |
| 开发时间 | 15 分钟 | 数周 |
| 能否独立使用 | ✅ 完全可以 | ❌ 必须依赖服务端 |
| 能否稳定使用 | ✅ 稳定 | ❌ 模拟设备会被风控 |
| 维护成本 | 低 | 极高（SDK 更新会失效） |

## 五、结论与建议

### 5.1 核心结论

**v4 签名（推荐）**：
- ✅ 算法完全确认
- ✅ 只需两个密钥即可模拟
- ✅ 不依赖真实设备
- ✅ 所有接口都支持
- ⏳ 等脱壳后 15 分钟完成

**v5 签名（不推荐逆向）**：
- ✅ 机制完全分析清楚
- ❌ 依赖数美服务端（无法独立使用）
- ❌ 需要真实设备指纹（模拟会被检测）
- ❌ 成本极高，收益为零

### 5.2 为什么 v4 已经足够？

**理由 1：麦当劳仍保留 v4 支持**
- v5 是渐进式部署，不是强制替换
- 所有接口都支持 v4
- 失败会自动降级到 v4

**理由 2：v4 签名已经很安全**
- HMAC-SHA256 是行业标准
- 请求头和 Body 都签名
- 密钥长度足够（推测 32 字节）

**理由 3：风控不是主要障碍**
- v5 主要防范恶意刷单、黄牛
- 正常频率的个人使用不在高风险范围
- 即使触发风控，v4 签名仍然有效

### 5.3 实际建议

**推荐路径**：
1. 等待麦当劳 SO 脱壳完成（3-5 天）
2. 提取 v4ak 和 v4sk 密钥（15 分钟）
3. 填入 `mcdonald_api_auth.py` 并测试
4. 完成登录、下单等所有功能

**不推荐**：
- ❌ 逆向 TDRisk SDK（成本极高，无法独立使用）
- ❌ 尝试绕过 v5 风控（会被检测）
- ❌ 集成官方 TDRisk SDK（需要数美授权）

---

**总结**：v4 签名完全够用，v5 签名无法真正模拟。等脱壳完成后专注于 v4 即可。
